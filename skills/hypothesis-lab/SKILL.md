# hypothesis-lab — 스폰지타임즈 가설 검증 OS

스폰지타임즈 3기의 운영 단위는 "발행"이 아니라 **가설 검증 루프**다.
이 스킬은 그 루프 전체 — 가설 수립 → 실험 설계 → 발행 → 수치 수집 → 검증·판정 → 베이스라인 갱신 —
를 하나의 시스템으로 굴리기 위한 OS다. 목표: 팔로워 500 → 1,000명 (@spongeclub.ai).

## 불변 원칙

이 원칙들은 어떤 모드에서도 지켜라. 원칙이 무너지면 "검증"이 아니라 "감상"이 된다.

1. **가설은 딱 한 문장.**
   `[누구]에게 [어떤] 훅으로 [어떤] 포맷을 보여주면 [어떤 반응]이 올 것이다.`
2. **[어떤 반응]에는 측정 가능한 지표와 임계값이 들어간다.**
   저장·공유·조회수·프로필 방문·댓글·비팔로워 도달 중 하나 + 기준(예: "저장률이 베이스라인의 1.3배 이상").
   "반응이 좋을 것이다" 같은 모호한 예측은 **받아주지 말고**, 지표와 임계값을 되물어라 —
   검증할 수 없는 가설은 루프를 돌릴 수 없기 때문이다.
3. **한 주에 변수 하나만 바꾼다.** 두 개를 바꾸면 무엇이 효과를 냈는지 알 수 없다.
4. **브랜드 고정 요소는 실험 대상이 아니다**: 노랑 악센트(형광펜·스티커), 첫 장 후크 문장 구조,
   계정 핸들·로고 위치, 캐릭터 스티커.
5. **정직한 비교만 한다.** 인스타그램 단일 계정에서 진짜 A/B 테스트는 불가능하다.
   가능한 것은 준실험(베이스라인 비교·짝비교·전후 비교)뿐이고, 교란변수를 기록해야
   결과를 믿을 수 있다. → `references/experiment-design.md`

## 지금 이 계정이 서 있는 자리

가설을 세울 때 이 진단을 기억하라 (2026-08-26 계정 분석 기준, `data/baseline.json`의
`account_profile`에 수치 보관):

- **병목은 생산량이 아니라 도달·확산이다.** 게시물 123개 · 팔로워 500명.
  레퍼런스 계정(@ourproject_chisang)은 게시물 수가 124개로 사실상 같은데 팔로워는 171배다.
  "더 많이 만들기"로는 풀리지 않는다는 근거이자, 3기가 가설 검증 루프를 도입한 이유.
- **이미 검증된 승리 공식이 있다.** 상위 3개 게시물 전부
  `실명·직업이 특정된 인물 + 숫자화된 결과 + Before→After 변화 서사` 구조였다
  (예: 커피 디자이너 8명→214명). 이걸 예외가 아니라 기본 포맷으로 쓰는 게 출발점.
- **약점 셋**: ① 절대 인게이지먼트가 낮다(평균 좋아요 14·댓글 3) ② 캡션이 길고 복잡해
  핵심이 뒤에 있다 ③ 콘텐츠발 팔로우가 시딩 8건 전부 0.
- **댓글:좋아요 = 0.21:1** (레퍼런스는 0.98:1). 댓글 CTA를 구조적으로 쓰지 않고 있다는 뜻.

## 데이터가 사는 곳 (환경 감지와 폴백)

이 스킬은 두 환경에서 쓰인다. 시작할 때 어느 쪽인지 감지하고 그에 맞게 동작하라.

| | Claude Code (레포 접근 가능) | claude.ai (스킬 zip 업로드) |
|---|---|---|
| 데이터 정본 | `data/*.csv` + Google Sheets 동기화 | Google Sheets |
| 읽기 | CSV 직접 → 필요 시 시트(MCP) | 시트(MCP) → 없으면 사용자에게 표 붙여넣기 요청 |
| 쓰기 | CSV에 행 append **+ 시트 붙여넣기용 TSV 블록 출력** | TSV 블록 출력 (사용자가 시트에 붙여넣기) |
| 분석 | `scripts/analyze.py` (차트 포함) | 인라인 계산 (주당 2~3개 포스트 규모라 충분) |

읽기 폴백 사다리: ① `config.json`의 `sheet_id`로 Google Drive MCP 읽기 →
② MCP 검색으로 시트 이름 찾기 → ③ `data/*.csv` → ④ 사용자에게 해당 로그 붙여넣기 요청.
어떤 경로로 읽었는지 사용자에게 한 줄로 알려라. 시트 구조와 쓰기 규칙은 `references/sheet-setup.md`.

**어느 환경이든 행을 기록할 때는 항상 시트에 그대로 붙여넣을 수 있는 TSV 블록을 함께 출력한다.**
(Drive MCP의 셀 단위 편집은 신뢰할 수 없다. 사람이 붙여넣는 것이 가장 확실한 동기화다.)

## 주간 루프와 모드

3기 운영 리듬: **월 가설 → 수 계획·피드백 → 토 발행 마감 → 일 24시간 데이터 검증.**

| 요일 | 할 일 | 모드 |
|---|---|---|
| 상시 | 레퍼런스 발견하면 바로 쌓기 | ⓪ 레퍼런스 수집·해부 |
| 월 | 이번 주 가설 세우기 | ① 가설 수립 → ② 실험 설계 |
| 수 | 콘텐츠 계획서 + 상호 피드백 | (제작은 캐러셀 앱에서) |
| 토 | 발행 마감 | ③ 발행 기록 |
| 일 | 24시간 데이터로 검증 | ④ 수치 수집 → ⑤ 검증·판정 → ⑥ 베이스라인 갱신 |

## 모드 ⓪ 레퍼런스 수집·해부

**트리거**: 타 계정 캐러셀·릴스의 이미지/영상/링크 공유, "레퍼런스 쌓아줘",
"이 계정 뜯어보자", "이거 참고해", "벤치마킹"

지금 가설에 안 쓰더라도 상관없다 — 이 모드의 역할은 **적용 포인트를 계속 축적**해서,
월요일 가설 수립 때 재료가 이미 쌓여 있게 만드는 것이다. 절차는
`references/reference-analysis.md`를 따른다. 요약:

1. **콘텐츠 수신**: 이미지·영상은 직접 분석한다. 링크는 인스타그램 로그인월 때문에
   내용을 못 여는 경우가 많으니, 열리지 않으면 링크·계정·포맷 등 메타만 기록하고
   **화면 캡처를 요청**한다 (캡처가 가장 확실한 전달 방식).
2. **3칸 해부** (콘텐츠마다): 고정 요소(매 편 똑같은 것) / 변수 요소(편마다 바뀌는 것) /
   후킹 요소(손이 멈춘 이유 — 릴스는 첫 3초, 캐러셀은 표지 문구).
3. **필수 질문**: "이걸 스폰지타임즈에 적용한다면?" — 이 답(`apply_point`)이 없으면
   해부가 끝난 게 아니다. "좋았어요"로 끝나지 않기.
4. **가설 후보 초안**: 적용 포인트를 한 문장 가설 형태(지표 포함)로 미리 써 둔다.
   바로 쓰지 않으면 `status=보관`으로 쌓아둔다.
5. **기록**: `references` 로그에 행 append + 시트 TSV 블록 출력. 여러 콘텐츠를 한 번에
   받았으면 각각 해부한 뒤 **공통 패턴 요약**을 덧붙인다.

**출력**: 콘텐츠별 해부 카드 + references 행(TSV) + (여러 건이면) 공통 패턴 요약.

## 모드 ① 가설 수립

**트리거**: "가설 세우자", "이번 주 가설", "가설 카드 만들어줘"

1. 베이스라인을 로드한다 (`data/baseline.json` 또는 시트 README 탭의 요약 블록).
   베이스라인이 없으면 → 모드 ⑥ 시딩을 먼저 제안하라. 기준 없는 가설은 임계값을 정할 수 없다.
2. **레퍼런스 로그(`references`)에서 `status=보관`인 적용 포인트·가설 후보를 먼저 확인**하고,
   이번 주 변수와 맞는 것이 있으면 제안한다 (모드 ⓪에서 쌓아둔 재료가 여기서 쓰인다.
   가설로 채택되면 해당 레퍼런스의 `status`를 `가설화됨`, `linked_hypothesis_id`를 기입).
3. 부족한 요소를 인터뷰로 채운다: 이번 주 실험 변수(config의 주차 계획 참고), [누구], [어떤 훅],
   [어떤 포맷], [예측 반응].
4. 한 문장 형식을 강제한다. 모호한 예측은 원칙 2에 따라 되묻는다.
5. `success_threshold`는 반드시 베이스라인 상대식으로 쓴다
   (예: `save_rate ≥ baseline carousel save_rate × 1.3`). 절대값 목표는 팔로워가 늘면 낡는다.
6. `templates/hypothesis-card.md` 형식으로 카드를 렌더하고, `hypotheses` 로그에 행을 기록한다.
   ID 규칙: `H-S3W1-01` (시즌-주차-일련). → `references/schema.md`

**출력**: 가설 카드 + hypotheses 행(TSV 블록 포함).

## 모드 ② 실험 설계

**트리거**: "실험 설계", "비교 어떻게 해", "대조군 어떻게 잡아"

1. `references/experiment-design.md`를 읽고 가설에 맞는 비교 방식을 고른다:
   - **baseline** — 최근 4주 같은 포맷 롤링 평균과 비교 (기본값)
   - **paired** — 같은 주에 변수만 다른 포스트 2개를 짝지어 비교 (가장 강한 설계)
   - **prepost** — 변수 도입 전/후 기간 비교
2. 교란변수 체크리스트를 함께 작성한다: 게시 시간대, 요일, 주제 강도, 팔로워 수 드리프트,
   외부 유입 이벤트(스토리 리셰어, 공유회 등).
3. 표본이 작으면 작다고 말하라. 포스트 1~2개 차이는 운일 수 있다 —
   판정 시 "판단불가"가 나올 수 있음을 미리 공유하는 것이 정직한 운영이다.

**출력**: 설계 블록(비교 방식 + 교란 체크) → 가설 행의 `comparison_design` 갱신.

## 모드 ③ 발행 기록

**트리거**: "발행했어", "올렸어", "발행 기록해줘"

1. 메타를 수집한다: 발행 일시, 포맷, 발행자, 연결 가설 ID(없으면 공란 = 대조군 후보),
   실험 변수의 실제 값, 주제 한 줄, 링크.
2. `post_id`를 발급한다 (`P-S3W1-01`). 지표 컬럼은 공란으로 두고 행을 만든다.
3. 다음 액션을 안내한다: "24시간 뒤 인사이트 스크린샷을 찍어서 올려주세요. 7일 뒤 한 번 더."

**출력**: posts_metrics 메타 행(TSV 블록) + 가설 행 `status` → `발행됨`.

## 모드 ④ 수치 수집 (스크린샷 파싱)

**트리거**: 인스타그램 인사이트 스크린샷 업로드, "수치 기록", "숫자 읽어줘"

1. `references/screenshot-parsing.md`의 용어 대응표로 스크린샷에서 지표를 추출한다.
   화면 캡처 시점으로 스냅샷(`24h`/`7d`)을 판별하고, 애매하면 물어본다.
2. 어느 포스트의 수치인지 매칭한다 (발행일·표지 이미지·캡션으로 추정 → 확인 질문).
3. 스크린샷에 없는 필드는 **0으로 채우지 말고 공란으로** 두고, 중요한 결측
   (도달, 저장, 팔로워/비팔로워 비율)은 추가 화면을 요청한다.
4. 파생지표를 계산해 기입한다: `save_rate = saves/reach`, `share_rate = shares/reach`,
   `follow_conv_rate = follows/reach`. 원시값이 진실이고 파생값은 편의다.
5. 행을 완성한다. 포스트당 스냅샷마다 1행 (append-only — 같은 포스트의 24h 행과 7d 행은 별도 행).

**출력**: posts_metrics 완성 행 + TSV 블록. (Claude Code면 CSV에도 append)

## 모드 ⑤ 검증·판정

**트리거**: "검증하자", "판정해줘", "가설 맞았어?", "이 콘텐츠 어땠어"

1. 대상 가설과 실험군 포스트, 설계된 대조 기준을 로드한다.
2. 비교한다: 실험값 vs 대조값, 차이(%), 임계값 충족 여부.
   Claude Code 환경이면 `scripts/analyze.py`를 실행해 비교표·퍼널·차트를 생성하고,
   아니면 인라인으로 같은 계산을 한다. 판정 기준은 `references/analysis-guide.md`.
3. 퍼널을 진단한다: 노출 → 조회 → 저장/공유 → 프로필 방문 → 팔로우.
   어느 단계에서 이탈했는지에 따라 해석이 다르다
   (노출 대비 조회 낮음 = 표지 후킹 실패, 저장·공유 낮음 = 다시 볼 가치 부족,
   프로필 방문 대비 팔로우 낮음 = 그리드 전환 실패 등).
4. 판정한다: **지지 / 기각 / 판단불가** — 근거와 함께. 교란변수가 결과를 설명할 수 있으면
   솔직하게 판단불가로 두는 것이 데이터를 지키는 길이다.
5. `templates/verdict-report.md`로 리포트를 렌더하고 `verdicts` 행을 기록한다.
   기각도 성과다 — `learning`에 배운 점과 다음 가설 제안을 반드시 채워라.
6. 모드 ⑥으로 베이스라인 갱신을 제안한다.

**출력**: 검증 리포트 + verdicts 행 + (Claude Code) `data/reports/` 스냅샷.

## 모드 ⑥ 베이스라인 관리

**트리거**: "베이스라인", "시딩", "2기 데이터 넣자", "기준값 갱신"

**시딩(최초 1회)**: 계정에 아직 지표 로그가 없다. 시즌2 포스트들의 인사이트 스크린샷을
일괄로 받아 모드 ④ 절차로 반복 파싱 → 포맷별 평균을 계산해 `baseline.json`을 만든다.
스크린샷 확보가 어려우면 알려진 집계(팔로워 360→440, 도달 중 팔로워 88.2%,
대표 포스트 저장 1·공유 0)로 임시 시드를 만들고, `"quality": "rough"`로 표시한다.

**갱신(검증 후마다)**: 최근 4주 롤링 윈도우로 포맷별 평균을 재계산하고
`history`에 이전 값을 남긴다. 갱신했으면 시트 README 탭의 베이스라인 요약 블록도
새로 붙여넣도록 TSV/텍스트 블록을 출력한다. 상세 규칙: `references/baseline-guide.md`

## 이 OS를 디벨롭할 때

이 스킬은 유닛 활동을 통해 계속 발전시키는 살아있는 OS다. 개선 요청이 오면:
- 가설 수립 파트 → 모드 ①·② 및 `experiment-design.md`
- 콘텐츠 제작 파트 → 캐러셀 앱(레포 루트의 Next.js)과의 연결 지점
- 데이터 확인 파트 → 모드 ④ 파싱 규칙 또는 향후 Instagram Graph API 수집기
  (스키마가 동일하므로 API 수집기는 `source=api`로 같은 행을 append하면 된다)
변경 시 `references/schema.md`의 컬럼 계약은 깨지 않는 것이 원칙이다 — 시트·CSV·API가 모두 이 계약 위에 서 있다.
